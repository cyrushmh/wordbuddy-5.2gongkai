## 一 · 工程定位与整体结构

`classics-harmony-app` 是一个**合规的 HarmonyOS NEXT（Stage 模型）应用骨架**，业务定位为「道家经典阅读 + 无障碍/适老化 + 组网协同」。它不是 toy demo，而是**一个可独立出 HAP 的完整工程**：

```
classics-harmony-app/
├── AppScope/app.json5            # 应用级：bundleName / version / icon / label
├── build-profile.json5           # 构建配置（签名初始为空，DevEco 首跑写入）
├── oh-package.json5              # 工程依赖（hypium / hamock 测试）
├── hvigorfile.ts                 # hvigor 构建入口
├── code-linter.json5            # 代码规范（ArkTS 规则）
├── build_hap.sh                  # 一键出包（需 SDK 工具链）
├── BUILD.md                      # 出包说明与占位替换清单
└── entry/src/main/
    ├── ets/
    │   ├── entryability/         # UIAbility 入口（生命周期）
    │   ├── entryformability/     # FormExtensionAbility（服务卡片）
    │   ├── pages/                # Index / BookDetail / ChapterDetail / DaozangViewer
    │   ├── widget/pages/         # WidgetCard（桌面卡片）
    │   ├── model/                # ClassicsData / ReaderPrefs / Accessibility / DeviceSync / ...
    │   └── component/            # ★ 73 个可复用构建块（本文分析主体）
    ├── module.json5             # 模块/能力/页面注册 + 权限声明（DISTRIBUTED_DATASYNC 等）
    └── resources/               # 字符串 / 颜色 / 媒体占位
```

**构建块总规模**：`component/` 73 个 `.ets`（约 4560 行），覆盖 UI、媒体、数据、设备能力、网络、图形、分布式、无障碍、应用框架九大域。样本批次（B24–B39）累计 **65 个**由旧代（Java API8 / JS FA）翻写而来，其余为工程原生设计块（如 `SearchInput`、`TaijiDecor`、`BottomTabs`、`Accessibility` 中枢等）。

## 三 · NEXT 核心范式提炼（从 73 块反推的本质）

1. **Stage 模型**：UI 与逻辑分离。`UIAbility` 管生命周期与窗口，`Page`（`@Entry @Component`）管界面，`ExtensionAbility` 管卡片/后台。`module.json5` 集中注册能力与权限。
2. **声明式 ArkUI**：UI = 组件树 + 链式属性调用（`.width().fontSize().onClick()`）。状态驱动（见下）自动重绘，开发者不手动操作 DOM。
3. **状态管理（驱动重绘的引擎）**：
   - V1：`@State`（组件内）/ `@Prop`（父→子单向）/ `@Link`（父↔子双向）/ `@Provide`+`@Consume`（跨层）/ `@Observed`+`@ObjectLink`（嵌套对象）/ `@Watch`（变更通知）。
   - V2（搜索补全）：`@ObservedV2`/`@Trace`（属性级细粒度更新）、`@Local`/`@Param`/`@Once`/`@Event`，性能优于 V1。
   - **本工程块大量使用 `@State` + 双向 `@Link`/`@StorageLink` 模式**（如 `SliderView`/`SwitchView`/`LikeToggle`），符合官方「优先 `@State`+`@Prop`/`@Link`，跨层才用 `@Provide`/`@Consume`」的建议。
4. **ArkTS 语言约束（编译型锚点）**：强制静态类型（禁 `any`/`unknown`）、禁止运行时变更对象布局（不能动态增删字段）、不支持 `eval`、类属性必须显式初始化、严格空安全。方舟编译器据此做字段偏移预计算、方法内联，**性能接近编译型语言**。
5. **权限模型**：`module.json5` 声明式声明（`DISTRIBUTED_DATASYNC`/`INTERNET`/`MICROPHONE` 等）+ 运行时 `PermissionHelper` 动态授权。敏感能力（定位/麦克风/相册）必须双轨。
6. **模块化 `@kit.*` 体系**：能力按 Kit 归类（AudioKit/ArkUI/MediaKit/CameraKit/ArkData/ConnectivityKit/...），导入即能力边界。本工程所有块顶部 `import { ... } from '@kit.Xxx'`（⚠️ 勘误：实测仍有 9 处散装 `@ohos`，主要为第三方库 `photoview`、待核验旧包名与 type-only `common`，非系统性违规，详见 `docs/02` §二），以 `@kit` 为绝对主体（90/99 import）。
7. **Canvas 命令式绘制**：与声明式 UI 互补，用于游戏/图表（`ChartCanvas`/`TetrisGame`/`SliderPuzzle`），遵循「context 独占 + `invalidate()` 刷新」。

## 四 · 全网搜索补全完善（基于 5 轮检索的结论）

### 4.1 API 版本演进（补全时间线）
| 系统版本 | API Level | 关键里程碑 | 与本文关系 |
|---|---|---|---|
| HarmonyOS 2.0 | 6–7 | 多设备类型 | — |
| HarmonyOS 3.0 | 7–8 | **引入 Stage 模型** | 旧代 Java API8（样本源）即此前的 FA 模型 |
| HarmonyOS NEXT | 9 | 纯血鸿蒙起点（去 AOSP） | 本工程目标代际 |
| HarmonyOS 5.0 | **12** | **NEXT 重大飞跃，新增 200+ API**（AI/3D/端侧大模型/OpenGL ES 3.2/Vulkan） | 本工程骨架基准 |
| HarmonyOS 5.0.4 | 16 | 三方 SDK（高德等）适配基线 | 升级候选 |
| （里程碑） | **24** | 社区称 NEXT 又一里程碑版本 | 关注，非当前目标 |

> 结论：**本工程以 API 12 为基准骨架，结构合规、可向 API 16/24 平滑升级**（仅需跟随 `@kit` 接口微调，无模型级破坏）。

### 4.2 状态管理 V1/V2 对照（补全）
| 场景 | V1 | V2（推荐新写） |
|---|---|---|
| 组件内状态 | `@State` | `@Local` |
| 父子单向 | `@Prop` | `@Param` |
| 父子双向 | `@Link` | `@Param` + `@Event` |
| 跨层共享 | `@Provide`/`@Consume` | `@Provider`/`@Consumer` |
| 嵌套对象 | `@Observed`/`@ObjectLink` | `@ObservedV2` + `@Trace`（属性级） |
| 变更监听 | `@Watch` | `@Trace` 自动 |

> 建议：新块优先 V2；存量 73 块为 V1（兼容 API 12），**不影响出包**，仅在性能敏感场景考虑迁移。

### 4.3 布局性能（补全官方最佳实践）
- **减少嵌套**：移除冗余 `Column`/`Row` 包装，用 `RelativeContainer`/`Grid`/`List` 替代深嵌套。
- **增量布局 + AsyncMeasure**：ArkUI 3.0 后仅重算变更部分，复杂嵌套支持异步测量。
- **渲染控制**：`@Reusable`（列表项复用）、`LazyForEach`（长列表）、`if/ForEach` 谨慎使用。
- 本工程 `ImageCarousel`/`VideoFeed` 已用 `Swiper`/`LazyForEach`，方向正确。

### 4.4 需关注的新能力（补全，可供后续块扩展）
- 端侧大模型推理 API（API 12+）：可给「道家经典」加本地问答。
- `CoreVisionKit`：图像语义搜索（`ImageKeywordSearch` 已用）。
- 3D 图形（3DGS/OpenGL ES 3.2/Vulkan）：未来可做经典卦象 3D 可视化。

## 五 · 跨语言 / 编译语言映射（核心交付）

> 目标：把 NEXT/ArkTS 的机制映射到其它主流语言与编译型 UI 框架，验证「NEXT 在约束上趋近编译型语言，在体验上保留 JS 系声明式」的判断，并回馈整体设计。

### 5.1 总对照表
| 维度 | **HarmonyOS NEXT (ArkTS)** | **SwiftUI (Swift)** | **Jetpack Compose (Kotlin)** | **Flutter (Dart)** | **Rust (iced)** | **C++ (Qt Quick/QML)** |
|---|---|---|---|---|---|---|
| 声明式范式 | ArkUI 组件树 + 链式属性 | 视图组合 + 修饰符 | `@Composable` 函数 | `Widget` 树 | 结构体 + `Element` + 消息 | QML 声明 + C++ 后端 |
| 状态→UI | 装饰器自动驱动重绘 | 属性包装器驱动 | 重组（recomposition） | 重建/InheritedWidget | `message` 订阅重绘 | 属性绑定 + 信号槽 |
| 组件内状态 | `@State` → `@Local` | `@State` | `mutableStateOf` + `remember` | `StatefulWidget` | `struct` 字段 + `on` 改 | `property` + `Binding` |
| 跨组件状态 | `@Provide`/`@Consume` → V2 `@Provider`/`@Consumer` | `EnvironmentObject` | `CompositionLocal` / ViewModel | `Provider`/`Riverpod` | 全局状态结构 | 单例/`Context` 属性 |
| 布局原语 | Row/Column/Stack/Flex/RelativeContainer | HStack/VStack/ZStack | Row/Column/Box/ConstraintLayout | Row/Column/Stack | `row!`/`column!` | Row/Column/anchors |
| 列表复用 | `LazyForEach` + `@Reusable` | `LazyVStack` | `LazyColumn` | `ListView.builder` | `scrollable` | `Repeater`/`ListView` |
| 语言类型 | 静态强类型（TS 超集，禁 `any`） | 静态强类型（值/引用语义） | 静态强类型（空安全） | 强类型（可空标注） | 静态强类型（所有权） | 静态强类型 |
| 编译模型 | 方舟编译器 **AOT**，禁运行时改布局 | 前端 + **LLVM AOT** | Kotlin 编译器 + R8 | Dart **AOT/JIT** | **LLVM AOT** | moc + 编译器 |
| 动态性 | 无（禁 `eval`/动态字段） | 有限（反射受限） | 有限（反射） | 有限（mirrors） | 编译期确定 | QML 运行时 JS 绑定 |
| 响应式本质 | 编译期插桩状态依赖 | 结构一致性比对 | 位置记忆重组 | 不可变 Widget 比对 | 订阅-通知 | 属性变更信号 |

### 5.2 映射结论（应用到整体）
1. **NEXT ≈ SwiftUI 的「声明式 + 状态装饰器」思路**，但语言基底是 JS 系 TS 超集而非 Swift；其 ArkTS 约束（禁 `any`、禁运行时改布局）让它在**编译期行为上更接近 Swift/Kotlin 编译型**，而非动态 JS。
2. **与 Compose 最像的是「状态驱动重组」哲学**；与 Flutter 最像的是「组件树 + 链式/Builder」；与 iced 最像的是「消息驱动重绘 + 纯函数视图」；与 Qt Quick 最像的是「声明式 + 属性绑定」。
3. **业务可移植性**：73 块中「纯 UI/布局/状态」块（TextView/TabListView/TableView/SliderView 等）可 1:1 映射到上述任一框架；「系统能力」块（Ble/Nfc/Location/分布式）强依赖 `@kit` 与鸿蒙运行时，**跨平台需重写底层**，但上层交互封装（状态/回调/错误降级）可复用。
4. **对 NEXT 自身的回馈**：73 块已普遍采用「状态封装 + 错误静默降级 + 权限双轨」模式，与 SwiftUI/Compose 的最佳实践同构——说明**声明式 UI 的「状态即真相、错误即降级」原则跨语言普适**，可作为后续新块的设计基线。
