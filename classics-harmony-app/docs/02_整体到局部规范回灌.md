# 整体→局部规范回灌（基于三条主轴的体检与回灌）

> 配套：`docs/01` 整体分析。本文是「整体分析反哺局部」的落地——以 `docs/01` 提炼的**三条主轴**（声明式 UI / 状态管理 / `@kit` 边界）为尺，对 73 个 `component` 块做一致性体检，把发现落成**可执行的局部回灌清单**。沙箱不可构建，故主体块不盲改；权限配置层缺口已**直接回灌**（低风险、消除真机崩溃）。

## 一 · 体检方法

- 聚合 `component/` 全部 `import { ... } from '@kit.*'` 分布（21 类 kit，累计 90 处）。
- 排查散装 `@ohos.*` import。
- 比对 `module.json5` 已声明权限 vs 能力块实际引用的 kit（蓝牙 / NFC / 定位 / 相机）。

## 二 · 发现一（更正 docs/01 §6.1 论断）

> ⚠️ **更正**：`docs/01` §6.1「全部 `@kit` 规范、无散装 `@ohos`」**不准确**。实测散装 `@ohos.*` 共 9 处：

| 文件 | 散装 import | 性质 | 建议回灌 |
|---|---|---|---|
| `ZoomImage.ets` | `@ohos/photoview` | 第三方 UI 库 | 补 `oh-package.json5` 依赖，或换 ArkUI 原生 `Image`+`PinchGesture`（该块已有手势） |
| `CommonEventBus.ets` | `@ohos.commonEventManager` | 系统能力旧包名（注释已标待核验） | 改 `@kit.NotificationKit` 的 `commonEventManager` |
| `DeviceLight.ets` | `@ohos.light` | 旧包名（待核验） | 查 `@kit.Device`/`@kit.SensorKit` 对应导出 |
| `KeyNavigation.ets` | `@ohos.multimodalInput.keyEvent` | 旧包名（待核验） | 改 `@kit.InputKit` 的 `KeyCode` |
| `LocalFileHelper` / `RelationalEntityStore` / `RemoteAbilityLauncher` / `RemoteAbilityController` / `BackgroundService` | `import type common from '@ohos.app.ability.common'` | type-only（ArkTS 惯用） | 可接受；若追求纯 `@kit` 可查 `@kit.AbilityKit` 的 `common` 类型导出 |

**结论**：21 类 `@kit` 已是绝对主体（90/99 import），散装仅为「第三方库 + 待核验旧包名 + type-only common」，**非系统性违规**。不作强制改写，仅列待核验项供 DevEco 批量核对。

## 三 · 发现二（权限缺口 · 已回灌 ✅）

`module.json5` 原仅声明 `DISTRIBUTED_DATASYNC` / `INTERNET` / `MICROPHONE`，但以下能力块在真机运行会因缺权限崩溃（即「毁灭」）：

| 能力块 | 所用 kit | 缺失权限 | 回灌动作 |
|---|---|---|---|
| `BleScanner` / `BtPeerFinder` | `ConnectivityKit`(ble) | `ohos.permission.USE_BLUETOOTH` | ✅ 已补 + `perm_bluetooth_reason` |
| `NfcController` | `ConnectivityKit`(nfc) | `ohos.permission.NFC` | ✅ 已补 + `perm_nfc_reason` |
| `LocationTracker` / `GeoCoder` | `LocationKit` | `ohos.permission.LOCATION` + `APPROXIMATELY_LOCATION` | ✅ 已补 + `perm_location_reason` |
| `CameraCapture` | `CameraKit` | `ohos.permission.CAMERA` | ✅ 已补 + `perm_camera_reason` |

> 回灌方式：直接改 `module.json5` 的 `requestPermissions` + `string.json` 的 reason 资源（配套补齐，不留构建隐患）。这是「整体→局部」最直接的实证——整体分析识别出缺口，局部配置即补，让能力块在真机「生存」。

## 四 · 三辩证落地示范：GoBoard.ets（新块）

- **整体与局部**：死活由整块棋的气决定（整体），单点急所可逆转全局（局部）——`collectGroup` 求连通组之气，`captureOpponent` 按整体气提子。
- **层次与平衡**：落子（输入层）→ 提子/禁着判定（状态层）→ Canvas 重绘（视图层）分明；声明式 `build` 与命令式 `draw` 互补平衡。
- **生存与毁灭**：`hasLiberty` 即生存，无气且未提子即被提（毁灭）；`onTap`/`draw`/`place` 均做越界与判空保护（工程上的「生存」= 错误静默降级）。
- 适老化：9/13/19 路一键切换、读屏播报、高对比木盘。

## 五 · 局部规范回灌清单（建议在 DevEco 批量应用）

基于三条主轴，局部块应统一遵循：

1. **导入边界**：优先 `@kit.*`；`type common` 保留；待核验旧包名查 `@kit` 对应（见 §二）。
2. **状态管理**：新块优先 V2（`@Local`/`@Param`/`@Event`）；存量 V1（`@State`/`@Link`）兼容 API12，**不强制改写**。
3. **错误降级（生存）**：系统能力块须 `try/catch` + 权限判空 + 失败静默降级，不阻断主流程（`DeviceSync`/`Accessibility` 已做，其余能力块建议抽查补）。
4. **读屏无障碍**：可交互元素 `accessibilityText`/`accessibilityDescription`；纯装饰 `accessibilityLevel(AccessibilityLevel.No)`（游戏/UI 块已做，装饰元素待补）。
5. **Canvas 规范**：context 独占 + `invalidate()` 刷新 + `onReady` 后绘制 + 判空降级（`ChartCanvas`/`TetrisGame`/`SliderPuzzle`/`GoBoard` 均遵循 ✅）。
6. **注释规范**：块头注明「旧代来源 → NEXT 翻写 → 概念 → 适老化」（B24–B39 块已遵循）。

## 六 · 总结

- 整体分析（`docs/01`）不是终点：它识别出「散装 `@ohos` 待核验」与「权限缺口」两类真实局部缺陷，并已将权限缺口**直接回灌**到 `module.json5` / `string.json`。
- 围棋 `GoBoard` 作为新块，示范三辩证的工程落地；后续新块照此基线。
- 主体 73 块未在沙箱盲改（不可构建、风险高），待 DevEco 按 §五清单批量核对即可。
