## 一、逐个分析（可学概念）

### 1. obs-studio —— C/C++ 跨平台媒体的「内核 + 插件 + 后端」范式

**结构实证**（来自克隆树）：
- 核心引擎 `libobs/`：`obs.h`、`obs-source.h`、`obs-scene.h`、`obs-output.h`、`obs-encoder.h`、`obs-module.h`、`obs-data.h`、`obs-properties.h`、`obs-hotkey.h` —— 一套 C API 描述「源 / 场景 / 输出 / 编码器 / 模块」。
- 渲染后端按平台切换：`libobs-d3d11`（Windows）、`libobs-metal`（macOS）、`libobs-opengl`（Linux）、`libobs-winrt` —— **同一接口、不同实现、编译期择一**。
- 功能全为可加载模块 `plugins/`：`linux-*` / `mac-*` / `win-*` 平台件，外加 `obs-ffmpeg`、`obs-x264`、`obs-webrtc`、`obs-browser`、`obs-transitions`、`obs-filters`、`obs-outputs`、`obs-websocket`、`image-source`、`text-freetype2` …… 经 `obs-module.h` 工厂注册。
- 构建：`CMakeLists.txt` + `CMakePresets.json` + `cmake/`；规范：`CODESTYLE.md` + `.clang-format` / `.swift-format`。

**可学**：
1. **内核 / 插件分离**：引擎稳定、能力外挂，新增功能不改动核心。
2. **平台后端替换**：跨平台的正解是「同一接口多实现 + 编译期选择」，而非 if 堆满业务代码。
3. **构建描述一次、处处可建**：`CMakePresets` ⇄ hvigor `build-profile.json5` ⇄ SwiftPM `Package.swift` 同一思路。
4. **代码规范即文档**：`CODESTYLE.md` + 格式化配置，团队规模协作的底座。

### 2. unicode-encoding-error-table —— 编码错配的「症状词典」

**内容**：古文码（GBK 读 UTF-8）、口字码（UTF-8 读 GBK）、符号码 / 拼音码（ISO8859-1 读 UTF-8/GBK）、问句码（GBK→UTF-8 二次错读）、锟拷码（UTF-8→GBK 二次错读）、烫烫烫 / 屯屯屯（VC Debug 未初始化内存）。

**可学**：中文文本对编码**极敏感**；导入外部文本必须「先判定编码再解码」，且失败要有损降级（替换为 `U+FFFD`）**而非崩溃**；乱码具备可识别指纹，可在导入预览时自检提示。

### 3. baochuquan/Books —— 书单目录（正面：分类意识）

**内容**：按 `Algorithm / Android / CS / Flutter / FrontEnd / OS / ProgrammingLanguage …` 等 20+ 主题分类的书单，README 承载书名清单 + 在线书链接。

**可学（正面）**：用**显式分类维度**组织书目。短板：元数据仅靠 README 文本、非结构化 —— 对经典文库应升级为「结构化元数据 + 显式分类」。

### 4. NicholasBxt/FreeBook —— 扁平文件库（反面：无分类 / 无元数据 / 无界面）

**内容**：根目录直接堆 `pdf / epub / ibooks / chm / docx`，仅靠文件名承载信息；无分类、无元数据、无阅读界面；大文件入 Git。

**可学（反面教材）**：书目稍多即不可检索；应建立「经史子集 + 书名/作者/朝代/卷数/注者」结构化元数据 + 检索与阅读界面；大文件宜走对象存储而非 Git。

## 二、应用回灌（落到代码）

### A. 三端数据契约对齐 + 元数据强化（来自 Books / FreeBook 教训）

**问题**：Swift `ClassicBook` 已有 `dynasty` / `category`，**ArkTS `ClassicBook` 缺** —— 三端契约不一致。

**修复**：
- ArkTS `model/ClassicsData.ts`：`ClassicBook` 增 `dynasty?` / `category?` / `volumes?` / `commentator?`；新增 `CLASSIC_CATEGORIES` 常量（经史子集道藏）。
- Swift `Model/ClassicsModels.swift`：增 `volumes?` / `commentator?`；新增 `ClassicCategory` 枚举（经史子集道藏，带中文 `label`）。

**效果**：两端契约一致；分类成为一等公民，可直接驱动书架分组 / 筛选。

### B. 编码安全导入工具（来自 uet 教训）

- ArkTS `util/TextEncoding.ets`：`decodeTextSafe`（BOM 剥离 → 严格 UTF-8 → 严格 GB18030 → 有损 `U+FFFD`）+ `looksLikeMojibake` 指纹自检；基于 `@kit.ArkTS` 的 `util.TextDecoder`。
- Swift `Utilities/TextEncoding.swift`：镜像实现（BOM → UTF-8 严格 → GB18030 严格 → 有损）。
- 用途：外部 `txt` 导入入口，防「锟斤拷 / 烫烫烫」污染正文，**绝不崩溃**。

### C. 架构同源确认（来自 obs-studio）

- 本工程已是「**组件即模块**（73 构建块可组合）+ **共享库跨端**（ArkTS NEXT 多设备 / Swift 共享库 iOS+mac）」，与 obs「内核 + 插件 + 后端替换」**同构**。
- 构建系统三件套对齐：`CMakePresets`(obs) ⇄ `build-profile.json5`(hvigor) ⇄ `Package.swift`(SwiftPM) 都是「描述一次、处处可建」。
- 规范即文档：obs 的 `CODESTYLE.md` ⇄ 本项目 `docs/00–03`。
