# 二十二、以概念系统为中心：重组网络模块与组网（v0.6.57）

## 一、为什么要重组

仓库里与「网络 / 组网」相关的子系统有 20+ 个，它们是**分批按需长出来的**：
`network`（协议调优）→ `osi`（七层诊断）→ `netlink`（链接协议 + 自组网）→ `meshchat`（连上之后聊什么）→
`distcompute` / `distjob`（算力与派活）→ `tor` / `zerotier` / `meshnet`（覆盖网）→
`dnshealth` / `vdns`（解析）→ `remote` / `tls13` / `cert`（安全审计）→ `apctrl` / `openwrt` / `edge`（设备）……
每个都有清晰的红线，但**彼此的层次位置、组网形态、依赖与互补关系**只散落在各自 docstring 里。

本轮以**仓库 wordbuddy-github 为主目录的概念系统**（与 `plang` 编程语言概念系统同构）把它们重组到一张图上。

## 二、四条分类轴

```
主目录（概念系统）wordbuddy-github
  ├─ 轴1 网络层次 layer（8）
  │    L1 物理(2) · L2 数据链路(5) · L3 网络(6) · L4 传输(5)
  │    L5-6 会话·表示(3) · L7 应用(15) · overlay 覆盖(3) · mesh 组网(5)
  ├─ 轴2 组网形态 form（8）
  │    standalone(5) · lan(5) · mesh(4) · overlay(2) · sdwan(1)
  │    distributed(3) · anonymous(1) · wan(6)
  ├─ 轴3 能力性质 nature（7）
  │    diagnose 只读诊断(11) · tune 调优 opt-in(1) · communicate 通信(2)
  │    share 共享(3) · audit 安全审计(5) · discover 发现(1) · reference 外部引用(1)
  └─ 轴4 标准依据 standard_basis：RFC / ISO / ITU（RFC 经 rfc_catalog 交叉验证）
```

**值得注意的分布**：
- **写操作面极窄**：24 个模块里只有 `network` 一个属于 `tune`（默认关闭、需 opt-in + 确认），其余 23 个全是只读或只给指引——这是本仓库一以贯之的红线纪律在分类上的直接体现。
- **L7 最密（15 个）**：DNS/HTTP/SSH/打印/消息/内容聚合都堆在应用层，而 `overlay`/`mesh` 两层把「组网」从 OSI 里单拎出来——OSI 模型本身没有覆盖网与自组网的位置，重组时显式补上。

## 三、依赖关系图（重组的核心产出）

**15 条关系边** = 5 条依赖 + 10 条互补：

```
osi          --depends--> network        # OSI 诊断复用 network 只读报告
meshchat     --depends--> netlink        # netlink 管「能不能连上」，meshchat 管「连上聊什么」
distjob      --depends--> distcompute    # 派活 = 调度计划 + 通道
distjob      --depends--> meshchat       # 经 meshchat 文本通道派 WU、收回结果
emergency    --depends--> network        # 网络+基站定位是首选基线

meshnet      <--complements--> zerotier  # 两种虚拟网思路（WireGuard 网状 ↔ SD-WAN 虚拟二层）
dnshealth    <--complements--> network   # 连接管理 ↔ 解析健康，分工不重复
vdns         <--complements--> dnshealth # 单域名解析 ↔ 虚拟根/多 CDN 选择
tls13        <--complements--> cert      # 协议态势 ↔ 证书与信任链
reshare      <--complements--> distcompute # 同人资源共享 ↔ 分布式算力
apctrl       <--complements--> openwrt    # AP 集中管理 ↔ 路由器系统
```

`build_netsys.py --check` 会校验**无悬空轴**（关系两端必须都是已登记模块）——
写错端点会静默失效，这是重组视图最容易坏的地方，故做成硬断言。

## 五、红线随模块登记

每个模块都带 `redline` 字段（24/24），例如：

- `distcompute`：「只跑内置可验证算子，**绝不下载或执行任何外部代码**」（与 BOINC 的根本差异）
- `distjob`：「通道里传的是参数不是代码；结果必须**复算校验**通过才算数，默认 dry_run」
- `meshchat`：「收到的文件**不自动落盘**，进待收清单由用户显式接受」
- `zerotier`：「不读 `identity.secret`（私钥）」
- `webnews`：「抓来的**永远是文本，无执行路径**——不 eval、不 subprocess」

`netsys redlines` 可一次性列出全部红线，作为越界防线的审计清单。

## 六、使用

```
sysweeper netsys                    # 概念系统速览（主目录/四轴/关系数）
sysweeper netsys layers             # 按网络层次看
sysweeper netsys form mesh          # 自组网形态下有哪些模块
sysweeper netsys nature audit       # 安全审计类模块
sysweeper netsys of distjob         # 单模块：层次/形态/性质/依赖/互补/标准/红线
sysweeper netsys relations depends  # 依赖图
sysweeper netsys rfc                # 引用的 RFC
sysweeper netsys redlines           # 全部红线
```

## 七、测试（11 项，`tests/test_netsys.py`）

- 规模与关系数（24 模块 / 8·8·7 轴 / 15 边 = 5 依赖 + 10 互补）
- 四轴取值齐备
- 具体分组正确（mesh 形态 4 个、audit 性质 5 个、**tune 仅 network 一个**）
- `of('distjob')` 依赖 distcompute + meshchat
- **无悬空轴**、**每模块都有红线**
- **每个 RFC 编号都能在 rfc_catalog 中查到**
- `build_netsys.py --check` 通过

> 本层只做「重组视图」——**不代调用**任何网络模块，也不改任何配置；
> 各模块自身的红线由各自实现保证。
