微软程序格式：PE / Portable Executable

Windows 加载一切可执行代码（.exe、.dll、.sys 驱动、.ocx 等）所依赖的底层文件格式。本文档基于《Windows Internals 7e》的镜像与加载机理整理，作为本资料库「磁盘优化 / Win10 整体优化」系列的第三根支柱——理解"程序到底长什么样、系统如何把它放进内存"。

PE32 / PE32+ DOS 头 · NT 头 节表 Sections 导入 / 导出表 重定位 加载器 Loader

①概述与文件类型

PE（Portable Executable，可移植可执行）是微软 32/64 位 Windows 采用的 executable / object / DLL 文件格式，由 COFF（Common Object File Format）扩展而来。它的设计目标是让同一个文件格式既能装"映像文件"（加载进内存执行），也能装"对象文件"（供链接器组合）。

支持的文件扩展名

.exe.dll.sys.ocx.scr.drv.cpl.efi

其中 .efi 是 UEFI 环境下的 PE 变体；.sys 是内核模式驱动，由 I/O 管理器加载（见本库「磁盘优化」方案中存储驱动栈一节）。

历史与变体

  • COFF：Unix 系 a.out 之后、微软接手改造的通用对象格式。
  • PE32：32 位 Windows，可选头 Magic = 0x10B。
  • PE32+：64 位 Windows（x64/ARM64），Magic = 0x20B，指针字段扩为 8 字节。
  • ROM 映像：极少用，0x107。
为什么重要：所有"程序慢 / 加载失败 / DLL 劫持 / 加壳检测"问题，最终都会落到 PE 结构的某个字段或某个目录上。看懂 PE，才能看懂 Windows 如何"把磁盘上的字节变成内存里跑的进程"。

③DOS 头与 Stub

每个 PE 文件都以一个 DOS 兼容头开头，目的是"在老 DOS 上运行时打印一句提示就退出"，同时保留 e_lfanew 字段指向真正的 NT 头位置。

字段偏移说明
e_magic0x00必须为 "MZ"（0x5A4D）—— 这是"是不是 PE"的第一道快速判断。
e_lfanew0x3C关键：4 字节，指向 NT 头（PE 签名）的文件偏移。几乎所有 PE 解析都先读这个。

DOS Stub：一段 16 位实模式代码，通常是 "This program cannot be run in DOS mode."。长度不固定，但 e_lfanew 总能带你越过它找到 NT 头。

快速校验伪代码： 
read e_magic @ 0  → must be "MZ"
read e_lfanew @ 0x3C → pe_off
read 4 bytes @ pe_off → must be "PE\0\0"
# 命中即确认这是一个 PE 文件

④NT / COFF 文件头

从 e_lfanew 处开始是 IMAGE_NT_HEADERS = 4 字节签名 PE\0\0 + IMAGE_FILE_HEADER + IMAGE_OPTIONAL_HEADER。

IMAGE_FILE_HEADER（COFF，20 字节）

字段含义
Machine目标 CPU：0x14C=x86, 0x8664=x64, 0xAA64=ARM64, 0x200=IA64。
NumberOfSections节的数量（决定节表有多长）。
TimeDateStamp链接时间戳（链接器写入，非文件创建时间）。
PointerToSymbolTable / NumberOfSymbolsCOFF 符号表位置（映像文件通常为 0）。
SizeOfOptionalHeader紧接其后的可选头大小（PE32=0xE0=224，PE32+=0xF0=240）。
Characteristics文件属性位图，如 0x2000=DLL、0x0002=可执行映像、0x0100=32 位字系统。

⑤可选头与关键字段

名字叫"可选"，对映像文件其实必选。它承载了加载器最需要的信息：入口点、内存布局、子系统、数据目录指针。

字段含义
Magic0x10B=PE32，0x20B=PE32+（64 位）。解析前先读它决定字段宽度。
AddressOfEntryPointRVA：程序入口（EXE 的 mainCRTStartup / DLL 的 DllMain）。加壳后常被指向解压 stub。
ImageBase期望加载的虚拟地址（EXE 默认 0x400000 / 64 位 0x140000000；DLL 默认 0x10000000）。
SectionAlignment / FileAlignment内存中节对齐（通常 0x1000=4KB 页）/ 文件中节对齐（通常 0x200 或 0x1000）。
SizeOfImage载入内存后映像的总大小（含所有对齐）。
Subsystem1=原生(驱动)，2=GUI，3=控制台(CUI)，9=WinCE，10=EFI。
DllCharacteristics见下方"安全特性"节（DYNAMIC_BASE=ASLR、NX_COMPAT=DEP 等）。
DataDirectory[16]16 个目录的（RVA, Size）对，指向导入/导出/资源/重定位等表。
对齐不一致是常见坑：磁盘上节之间可能有很多 0 填充（因为 FileAlignment），但内存中节地址由 SectionAlignment 决定——所以"文件偏移"和"RVA"之间不能简单相加，必须按节逐个换算（RVA→FOA 转换是 PE 解析的基本功）。

⑥数据目录（16 项）

DataDirectory 是可选头末尾的 16 个 {VirtualAddress, Size} 结构，是加载器定位各功能表的"目录"。索引如下：

#常量内容
0EXPORT导出表（EAT）
1IMPORT导入表（IAT + INT）
2RESOURCE资源（图标/对话框/版本信息）
3EXCEPTION异常表（x64 的 .pdata）
4SECURITY数字签名（Authenticode，位于文件末尾，不在内存映射中）
5BASERELOC基址重定位表
6DEBUG调试信息
7ARCHITECTURE保留
8GLOBALPTR保留
9TLS线程局部存储
10LOAD_CONFIG加载配置（CFG/安全 Cookie 等）
11BOUND_IMPORT绑定导入（加速，但可能过期）
12IAT导入地址表（运行时被填真实地址）
13DELAY_IMPORT延迟加载导入
14COM_DESCRIPTOR.NET / COM 运行时描述符
15RESERVED保留

注意 SECURITY（#4）是唯一不在内存映射中的目录——签名是附加在文件尾部、Verify 时才读取的，因此它不参与 VA 空间。

⑦节表与常见节

节表紧跟可选头之后，每个 IMAGE_SECTION_HEADER 40 字节，描述一节在文件与内存两边的位置/大小/属性。

字段含义
Name8 字节节名（.text/.data…），可自定义（加壳常用乱名如 .upx0）。
VirtualSize内存中该节实际大小（未对齐）。
VirtualAddressRVA：该节映射到的内存起始。
SizeOfRawData磁盘上该节占用大小（按 FileAlignment 对齐）。
PointerToRawData该节在文件中的偏移。
Characteristics属性位：0x20000000=可执行、0x40000000=可读、0x80000000=可写 等组合。

常见节

.text

代码（可执行、可读）

.rdata

只读数据：导入/导出的名称、常量

.data

已初始化全局变量（可读写）

.rsrc

资源树（图标/版本/对话框）

.reloc

基址重定位修复表

.pdata

x64 异常处理/展开表

RWX 是危险信号：一个节同时具有"可写 + 可执行"（W+X）通常是代码注入或加壳/打包的特征，杀软会重点盯。正常编译器产出的节会把"写"和"执行"分开。

⑧导入表

程序要调用别的 DLL（如 kernel32.dll 的 CreateFile），并不把代码塞进自己文件，而是记录"我需要哪些 DLL 的哪些函数"。加载时由加载器填好真实地址。

结构角色
ILT / INT（导入名称表）记录"需要什么"（函数名或序号），解析时作为参照。
IAT（导入地址表）运行前和 INT 相同；加载后被改写为函数真实地址，CPU 调用时直接跳这里。
Hint/Name/Ordinal定位函数的三种方式（按名、按序号、按提示序号）。
Bound Import预先绑定地址以加速，但 DLL 重定位后即过期，需重新解析。
Delay Load用到时才真正解析（如大型 COM/可选组件），减小启动开销。
安全关联 · DLL 劫持：导入表只写 DLL 名不写路径。加载器按"Known DLLs → 程序目录 → 系统目录…"的顺序搜索，若攻击者把同名恶意 DLL 放到搜索更靠前的目录，就会先被加载。这正是本库「Win10 整体优化」里"审计启动项/服务路径"要防的一类问题。

⑨导出表

DLL 用导出表对外暴露函数。核心是三张并行表：导出地址表 EAT（函数 RVA）、名称表、序号表。调用方可通过名称或序号查到函数入口。

  • NumberOfFunctions / NumberOfNames：导出总数 / 按名导出数。
  • AddressOfFunctions：EAT 数组（RVA）。
  • 转发（Forwarding）：导出项可指向 otherdll.exportname，实现 DLL 间的函数转发（系统常用）。

⑩重定位

代码里写死的绝对地址（如全局变量指针）都基于 ImageBase 假设。当映像无法按期望基址加载（被 ASLR 挪走或与其他 DLL 撞车）时，加载器需按 .reloc 表里的"修复记录"把绝对地址整体平移 Δ = 实际基址 - 期望基址。

为什么 DLL 必须可重定位：多个 DLL 共享 4GB(32位) 地址空间，冲突不可避免。EXE 通常能拿到首选基址（冲突少），但 DLL 几乎一定会被重定位——这就是重定位表存在的意义。IMAGE_FILE_RELOCS_STRIPPED 标志位（被 EXE 常见、DLL 致命）表示"本文件无重定位信息"。

⑪加载流程（加载器如何把 PE 变成进程）

当用户双击 .exe，Windows 走这条主线（与《Windows Internals》进程/内存/映射文件机理一致）：

步骤发生的事
1. 创建进程CreateProcess → 内核创建 EPROCESS/句柄表/地址空间（空）。
2. 映射映像以映射文件（Section 对象）方式把 PE 映像按节表放进新进程地址空间（注意：这是"内存映射文件"，呼应本库「磁盘优化」里缓存/映射文件一节）。
3. 重定位若实际基址 ≠ ImageBase，按 .reloc 修复绝对地址。
4. 解析导入逐个加载依赖 DLL → 填好 IAT（递归，依赖也有自己的导入）。
5. TLS / 安全执行 TLS 回调（早于 main！是恶意代码偏好点）、应用 CFG/DEP 等。
6. 跳入口调度器把线程指向 AddressOfEntryPoint，用户态程序开始跑。
性能关联：导入表越大、依赖 DLL 越多、需重定位越多 → 进程启动越慢、页错误（page fault）越多、冷启动 I/O 越重。这正是本库「Win10 启动优化」要砍开机项/清理依赖的根本原因——每一次"多加载一个 DLL"在 PE 层面都对应一串额外的导入解析 + 节映射 I/O。

⑫安全特性（DllCharacteristics / 目录）

现代 PE 通过可选头 DllCharacteristics 标志位声明它配合哪些 OS 安全机制：

标志机制作用
DYNAMIC_BASE (0x40)ASLR加载基址随机化，对抗 ROP/内存布局猜测。
NX_COMPAT (0x100)DEP数据页不可执行，防 shellcode 注入。
GUARD_CF (0x4000)CFG控制流保护，校验间接调用目标。
FORCE_INTEGRITY (0x80)强制签名校验加载前必须过签名（驱动/安全组件）。
目录 #4 SECURITYAuthenticode嵌入 X.509 签名，用于 SmartScreen/驱动签名。
加壳/混淆的识别（防御视角）：异常小的导入表 + 单一可执行节 + 入口指向解压 stub + 节名非标准 + 缺失正常安全标志，往往意味着程序被打包（合法如 Installer/保护器，也可能藏恶意代码）。识别它是为了审计，不是去拆解它。

dumpbin

pefile
