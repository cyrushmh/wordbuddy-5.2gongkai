# 37 · 各系统打包与安装教程（因地制宜 · 各自规范）

> 指令原文：「构建docker支持；如果需要构建安装包软件包的，给出教程文档在各系统目录，readme;继续」。
> 本档案按「因地制宜、各自规范」原则（仓库根 `docs/packaging.md` 总纲）给出
> **每个目标系统**的安装路径。sysweeper 本体是**纯标准库、零第三方运行时依赖**的
> Python 包，官方工件只有三种（不打系统专有包——理由见 §1）：
>
> | 工件 | 形态 | 构建命令 |
> |------|------|---------|
> | **.pyz**（推荐） | zipapp 单文件，带 shebang，`python3` 直接跑 | `python3 ../../tools/syspkg.py pyz --out dist` |
> | **wheel** | `py3-none-any` 纯 Python 轮子 | `python3 ../tools/syspkg.py wheel --out dist`（手写 PEP 427，不经由 setuptools） |
> | **sdist** | 源码分发包 | `python3 ../tools/syspkg.py sdist --out dist` |
>
> Docker 镜像另见 `36_Docker容器化与镜像构建.md`。

## 1. 为什么不打 .deb / .rpm / .pkg / MSI

「因地制宜」不等于「每个系统各打一个专有包」。sysweeper 的知识库是
`src/python/sysweeper/data/*.json`（随包分发），零依赖意味着**任何有 `python3` 的
机器都能跑同一份 `.pyz`**——这正是仓库 packing.md 说的「共同的需要集合、集合的分别应用」：
同一份工件服务所有系统，不按系统分裂维护 N 份。打专有包的代价（每发行版元数据、
每个版本的 repack、签名与仓库托管）远超收益。**能下载即可运行的兼容层就是它的分发形态。**

唯一例外已在仓库其他子项目落地（`classics-linux` 有 `debian/` 与 `PKGBUILD`），
那是 C 源码、需要原生编译的项目，与纯 Python 工具不是一类。

## 2. 通用前置条件

- **Python ≥ 3.8**（`python3 --version` 确认；pyz 在 3.9/3.10 由 `sysweeper/_zipres.py`
  补 `zipimport` shim，3.11+ 原生支持 zip 内读 JSON 知识库）
- 无需 pip、无需编译工具链、无需联网（.pyz 路径）
- 存储空间约 15 MB（含全部九系统知识库）

## 3. 分系统安装教程

### 3.1 Windows 10 / 11 / Server

**方式 A：.pyz 双击或命令行（推荐，零安装）**

```powershell
# 从 Release 下载 sysweeper-<版本>.pyz（或本地构建，见 §5）
python sysweeper-0000.0000.0000.0004.20261024.pyz detect
.\sysweeper-0000.0000.0000.0004.20261024.pyz detect        # .pyz 已带 shebang 与可执行位等价物（Win 上经 python 启动器关联）
```

> 若未关联 `.pyz` 到 python，用上面的 `python xxx.pyz` 形式即可。

**方式 B：pip 安装 wheel**

```powershell
pip install sysweeper-0000.0000.0000.0004.20261024-py3-none-any.whl
sysweeper detect                       # 安装后得到 sysweeper 命令
```

**方式 C：自包含 .bat（给不会用命令行的用户）**

```powershell
sysweeper genbat --out cleanup.bat     # 生成自带分析/执行/计划任务的批处理
```

**WSL**：进入 WSL 后按 Linux 路径执行（WSL2 里探测到的是 Linux 发行版，
要诊断 Windows 侧加 `--platform windows`）。

### 3.2 Linux（Debian / Ubuntu 及衍生）

```bash

# 方式 B：pip（系统级或用户级）
```

#### 附：classics-linux 原生 deb（13 架构 × 4 发行版全矩阵 · 2026-10 实测）

§1 提到的「唯一例外」子项目（C 源码、需原生编译）已按 **架构 × 发行版** 矩阵
产出真实可安装的 .deb，作为本仓库的 Debian/Ubuntu 打包范本：

| 维度 | 覆盖 |
|------|------|
| 架构 | amd64（原生）、arm64、armel、armhf、i386、mips、mipsel、mips64、mips64el、powerpc、ppc64el、riscv64、s390x（共 13 个，交叉工具链 `crossbuild-essential-*` 全套） |
| 发行版 | Ubuntu 24.04 (noble) / 22.04 (jammy)、Debian 13 (trixie) / 12 (bookworm) |
| 分包 | `classics`（Architecture: any，二进制 + man）+ `classics-data`（Architecture: all，典籍数据，避免各架构重复打包同一份数据） |

```bash
cd classics-linux
bash build-debs.sh            # 52 格全矩阵构建，产物与逐格日志落 build/
dpkg-deb -f build/classics_0001.0000.0000.0000.20261024~bpo12+1_arm64.deb Depends
# → libc6:arm64 (>= 2.34), classics-data (>= 0001.0000.0000.0000.20261024~bpo12+1)
```

发行版变体不经后缀仓库存放，而是按 changelog 的 version + distribution 区分
（`1.0.0ubuntu1` / `1.0.0~jammy1` / `1.0.0~bpo12+1` / `1.0.0`）。

**全架构构建的三个坑（均已修复，逐条实证）**：

1. **glibc 依赖过度收紧**：Ubuntu 交叉工具链的 libc 只有 `.shlibs` 没有
   `.symbols`，dpkg-shlibdeps 无法从符号表推导真实版本，会把依赖钉死在工具链
   libc 版本（本机 2.39）；而二进制 `objdump -T` 实测最高符号仅 `GLIBC_2.34`，
   直接发包会把 Debian bookworm（libc 2.36）用户误挡在门外。`debian/rules` 的
   `override_dh_gencontrol` 在 dh_gencontrol 读 substvars 前按 objdump 实测值改写
   `shlibs:Depends` 的 libc6 下限（原生 amd64 对照实验：改写前后一致，零副作用）。
2. **shlibdeps 找不到 sysroot 库**：`-l` 路径必须用 `DEB_HOST_GNU_TYPE` 而非
   `DEB_HOST_MULTIARCH`（i386 的 multiarch 名是 i386-linux-gnu，工具链实际装在
   `/usr/i686-linux-gnu/`）；且 mips64/mips64el 的动态链接器 `ld.so.1` 在
   `lib64/` 而非 `lib/`。现按存在性动态添加 `lib` 与 `lib64` 两个搜索路径。
3. **六架构默认无 PIE**：dpkg-buildflags 对 armel/mips/mipsel/mips64/mips64el/
   powerpc 不注入 PIE（lintian 报 `hardening-no-pie`）。Makefile 对这六个架构
   显式补 `-fPIE`/`-pie`，重建后全部为 `Type: DYN`，与其他架构 hardening 口径一致。

**验证口径**（全过才收工）：`dpkg-deb -f` 核对 52 包元数据 → `lintian` 56 包
（含 data 子包）零 E/W tag → `qemu-<arch>-static -L /usr/<triplet>` 解包实跑
13 架构 `list`（arm64/armhf/riscv64 另测 `show/decode/lint` 四子命令）。
完整交接单见 `classics-linux/HANDOFF-arm-deb.md`。

### 5.1 Windows 交叉编译（mingw-w64，无需 Windows 机器 · 2026-10 实测）

Linux 上装 mingw-w64 全家即可直接构建 Windows 原生 PE 二进制，wine 本机仿真验证：

```bash
sudo apt install mingw-w64 gcc-mingw-w64 g++-mingw-w64 wine   # x64/x86 双架构 + 仿真器
x86_64-w64-mingw32-gcc -O2 -static -o app.exe app.c           # → PE32+ (console) x86-64
i686-w64-mingw32-gcc   -O2 -static -o app32.exe app.c         # → PE32 (console) Intel 80386
x86_64-w64-mingw32-gcc -shared -o x.dll x.c -Wl,--out-implib,libx.a   # DLL + 导入库
WINEPREFIX=/tmp/wp WINEDEBUG=-all wine app.exe                # wine 实跑验证
```

实测结论：静态/动态 exe、DLL+导入、C++（iostream）、`clang --target=x86_64-w64-mingw32`
七种形态全部构建成功，wine 9.0 实跑全部通过。线程模型 posix/win32 双变体经
update-alternatives 切换。完整清单见仓库根 `docs/开发工具链安装报告.md`。

### 5.2 Android 交叉编译（NDK r26d，低 API 21/26 双架构 · 2026-10 实测）

「旧版开发比较多」口径：**API 21（Android 5.0，armeabi-v7a 最后广泛代）打底，
API 26（Android 8.0，项目既定下限）为准**，双架构 armeabi-v7a + arm64-v8a：

```bash
# NDK r26d（dl.google.com，约 640MB）
curl -fL -o android-ndk.zip https://dl.google.com/android/repository/android-ndk-r26d-linux.zip
unzip -q android-ndk.zip -d /opt/android-ndk
NDK=/opt/android-ndk/android-ndk-r26d/toolchains/llvm/prebuilt/linux-x86_64/bin

# hello 静态（API 21 / 26 × aarch64 / armv7a）
$NDK/aarch64-linux-android21-clang     -O2 -static -o hello_a64_api21 hello.c
$NDK/armv7a-linux-androideabi21-clang  -O2 -static -o hello_a32_api21 hello.c
$NDK/aarch64-linux-android26-clang     -O2 -static -o hello_a64_api26 hello.c
file hello_a64_api21    # → ELF 64-bit ARM aarch64, statically linked
```

**bionic 无 iconv——classics.c 的 GB18030 解码须自备**：NDK 自 r15 起不含 iconv，
交叉编译 GNU libiconv 1.17 补齐（双架构各编一份，静态链入，产物零动态依赖）：

```bash
tar -xzf libiconv-1.17.tar.gz && cd libiconv-1.17
CC=$NDK/aarch64-linux-android26-clang ./configure --host=aarch64-linux-android \
    --prefix=/opt/libiconv-android-a64 --enable-static --disable-shared
make -j4 && make install
# armv7a 同理换 --host=armv7a-linux-android --precise 换 CC 为 armv7a-linux-androideabi26-clang
$NDK/aarch64-linux-android26-clang -O2 -static -o classics_a64_api26 classics.c \
    -I/opt/libiconv-android-a64/include \
    /opt/libiconv-android-a64/lib/libiconv.a /opt/libiconv-android-a64/lib/libcharset.a
```

实测结论：hello × 4（API 21/26 × 双架构）+ classics × 3（API 21/26 a64、API 26 a32，
静态链入 libiconv）全部构建成功，`file` 判定 ELF64/ELF32 ARM、`llvm-readelf -d` 零
NEEDED（全静态），NOTE 段 `NT_ANDROID_TYPE_IDENT` 确认 NDK r26d。

> **运行级验证限制（如实标注）**：qemu-user 8.2.2 跑 bionic 二进制三连坎——
> ① aarch64 静态报 TLS 段对齐不足（`alignment is 8, needs 64 for ARM64 Bionic`）；
> ② armv7 静态报 `personality` 系统调用被沙箱拒绝；③ 动态链接 + libc.so 顶替
> linker64 后 linker 初始化 SIGSEGV。**构建级验证完整，运行级需真机/模拟器**
> （termux 或 adb push 后执行）。

### 5.3 HarmonyOS 交叉编译（OpenHarmony SDK 6.0.0.47 Linux · 2026-10 实测）

OpenHarmony 官方流水线提供 **Linux 版 ohos-sdk**（含 clang 15.0.4 交叉工具链，
目标 musl libc），华为云镜像即可下载：

```bash
# 约 2.4GB（repo.huaweicloud.com 镜像，版本目录以镜像站当前为准）
curl -fL -o ohos-sdk.tar.gz \
  https://repo.huaweicloud.com/openharmony/os/6.0-Release/ohos-sdk-windows_linux-public.tar.gz
tar -xzf ohos-sdk.tar.gz -C /opt/ohos-sdk
cd /opt/ohos-sdk/linux
unzip -oq native-linux-x64-*.zip toolchains-linux-x64-*.zip   # native 工具链 + 签名工具
OHOS=/opt/ohos-sdk/linux/native/llvm/bin

# 双架构：aarch64 + armv7（clang 15.0.4，目标 x-unknown-linux-ohos）
$OHOS/aarch64-unknown-linux-ohos-clang -O2 -o hello_ohos_a64 hello.c
$OHOS/armv7-unknown-linux-ohos-clang   -O2 -o hello_ohos_a32 hello.c
file hello_ohos_a64    # → ELF 64-bit ARM aarch64, interpreter /lib/ld-musl-aarch64.so.1
```

**musl 优势——qemu 直接实跑**（不像 bionic 三连坎）：

```bash
$OHOS/aarch64-unknown-linux-ohos-clang -O2 -static -o hello_ohos_static hello.c
qemu-aarch64-static hello_ohos_static    # → Hello, HarmonyOS! aarch64 build OK（rc=0）
```

**classics 直编 OHOS（musl 自带 iconv 且支持 GB18030，无需 libiconv）**：

```bash
$OHOS/aarch64-unknown-linux-ohos-clang -O2 -static -o classics_ohos_a64 \
    /path/to/classics-linux/src/classics.c
qemu-aarch64-static classics_ohos_a64    # → 用法正常输出（rc=0）
```

实测结论：hello × 2 + classics × 1 全部构建成功；OHOS 静态 aarch64/armv7 在
qemu-user 下**实跑通过**（musl 与 glibc 同属 qemu 友好目标）；动态链接运行需
`sysroot/lib → usr/lib` 软链补 linker 解析路径（qemu `-L` 前缀限制，如实记录）。
OHOS 原生应用（HAP/ArkTS）路径另见 `classics-harmony-app` 与 `windows-api-version-matrix.md`。
