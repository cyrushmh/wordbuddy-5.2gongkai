## 1. 为什么系统基座通向概念系统——一条「目录服务」主线

用户的三句话其实指向同一个根概念：**定位资源**。从单机到全网，定位资源的机制同构：

| 尺度 | 定位机制 | 本子系统的落点 |
|---|---|---|
| **系统目录** | FHS 用固定路径约定「系统/工具链/组件」各安其位 | `system_layout` 轴 |
| **包仓库** | apt/yum 用 suite/component/arch + 索引文件定位包 | `package_formats` / `network_repos` 轴 |
| **互联网** | DNS 把名字解析成地址、URL 在地址上定位资源 | `path_namespace` 轴（概念层供料） |
| **安全闭环** | 信任锚（GPG 公钥 / DNSSEC）决定「可被定位的资源是否可信」 | `msf_distro` 与 `cert` 桥接 |

这条主线把「系统/网络/安全」三轴统一到「目录服务」这一个根概念上——这就是「整合到概念系统」的落点：sysbase 在 linkage 里向 `packages`/`pkgmgr`/`network`/`cert` 四个概念轴桥接。

## 3. 轴一：系统目录（FHS / LFS）—— 什么是系统

- **FHS 3.0**：定义 `/bin /sbin /usr /var /etc /opt /run` 等目录的职责；`usrmerge` 把 `/bin /sbin /lib` 符号链接到 `/usr` 下的同名目录（现代发行版默认）。
- **LFS 口径回答三问**（Linux From Scratch）：
  - **什么是系统**：引导器 + 内核 + init + shell + coreutils + C 库，构成可自举运行的基底；
  - **什么是基础工具链**：binutils / gcc / glibc / linux-api-headers，先在宿主交叉编译出自持工具，再 chroot 进目标系统自举（LFS Book 第 5 章，顺序 binutils → gcc → glibc → linux-api-headers）；
  - **什么是系统关键组件**：内核 / init / udev / journald / shell / 包管理器 / C 库。
- **/opt 与 /usr/local**：发行版包管理器管辖之外的两个自建软件落点，`/opt/<pkg>` 常是第三方闭源（如 Metasploit 官方安装器）的落点——检测面必须覆盖。
- **机算落点**：`native/sysbase.py` 的 `probe_system_layout` 只读枚举 FHS 关键目录在位性、usrmerge 合并状态、`/opt` 附加软件清单。

## 4. 轴二：软件包格式与本地包管理器（deb / rpm）

- **deb** = `ar` 归档，含 `control` 与 `data` 两段；底层 `dpkg` 记账（数据库 `/var/lib/dpkg/status`），高层 `apt` 解依赖。
- **rpm** = 带头签名的 `cpio` payload；`rpm -q` 查数据库，`rpm -ql` 查文件清单。
- **deb 版本序**：`~` 表示「低于空」，`6.5.3~20260818061200~1rapid7-1` 中 `~20260818...` 是 nightly 时间戳，因此排在正式 `6.5.3` 之前；`-1rapid7` 是打包者/修订号。
- **检测面必须「数据库 + 文件系统」两路都查**：`dpkg -l / rpm -qa` 查已安装，但 **git 源码安装的软件在包数据库里没有记录**——只查数据库会漏。
- **机算落点**：`native/sysbase.py` 的 `probe_package_managers`（探测 dpkg/apt、rpm/yum/dnf、pacman/apk 存在性 + 查 metasploit 包记录）+ `parse_deb_version`（拆 upstream/nightly/打包者/修订号）。

## 5. 轴三：网络包管理器（apt / yum 仓库）

- **apt 信任链四步**：Release 文件用仓库公钥验签名 → 其 SHA256 校验 Packages 索引 → 索引里的校验和校验包体。**信任锚是登记的公钥，不是 HTTPS**——HTTPS 只保密不认证。
- **订阅即可信边界变更**：`/etc/apt/sources.list.d`（含 `signed-by` 精确绑定）、`/etc/apt/preferences.d`（pin 优先级）、`/usr/share/keyrings`（密钥）、`/etc/yum.repos.d`。
- **本机实录**：apt.metasploit.com 的 pin 为 **1000**（即使降级也优先装该源）。
- **仓库不校验客户端发行版**：`apt` 源写 `lucid` 在 `noble` 上照样装（suite 名只是索引路径）——这是「互联网即目录服务」在包仓库层的直接体现。
- **机算落点**：`native/sysbase.py` 的 `probe_network_repos` 只读盘点源/pin/keyring/yum repo。

## 6. 轴四：Metasploit 分发与检测（安全与检测）

- **官方渠道**：docs.metasploit.com 的 Nightly Installers + metasploit-omnibus（GitHub 官方安装器源码）；官方 `msfinstall` 走 **deb/apt** 路径。
- **安装路径判定**：二进制包（dpkg/rpm）vs git 源码克隆（`git clone github.com/rapid7/metasploit-framework`）。
- **检测三路覆盖**（只读，绝不启动利用）：
  1. **包数据库**（dpkg/rpm）：有无 metasploit-framework 记录；
  2. **文件系统**：PATH 中 12 个命令（msfconsole/msfvenom/msfupdate…）、`/opt` 安装目录、git 克隆目录；
  3. **仓库订阅**：sources.list.d / pin / keyring / yum.repo 四类 apt 痕迹。
- **本机实录**：官方 msfinstall 装的 `6.5.3~20260818061200~1rapid7-1`，本探针可完整检出——「装了就能报出来」。
- **红线**：不启动 msfconsole 跑任何模块、不生成载荷、不做任何扫描/利用；未授权环境出现 msf 痕迹即高信号。
- **机算落点**：`native/sysbase.py` 的 `probe_msf` + `msf_version_report`。

## 7. 轴五：路径与命名空间——用户三条概念课的落点

### 7.1 概念课①：安装包引用都是相对路径

绝对地址 = **基址 + 相对路径**，所以包可重定位（chroot / 容器 / 自定义前缀）。三实例（msf 实录）：

- **包内清单**：deb 的 `data.tar` 条目 `./opt/metasploit-framework/bin/msfconsole`（相对安装前缀）；
- **仓库索引**：`Packages` 的 `Filename: pool/main/m/metasploit-framework/xxx.deb`（相对仓库根）；
- **包装脚本**：`msfvenom` 用法行 `bin/../embedded/framework/msfvenom`（以 `$0` 相对的 `../` 定位真身）；
- **update-alternatives**：两跳符号链（`/usr/bin/xxx → /etc/alternatives/xxx → /usr/bin/xxx-<ver>`）。

### 7.2 概念课②：每个命令都有参数，要看文档与 `--help`，源代码也有文档

- 包管理器命令（`dpkg -l/-L`、`rpm -q/-ql`、`apt-get install --dry-run`）参数各异，**先 `--help` / man 再动手**；
- 本工具本身践行此课：`sysbase` 子命令 `--help` 即列出五轴与红线；native 探针函数 docstring 即文档；
- **灵活运用**：同一信息多路取证（包数据库 + 文件系统 + 仓库订阅），不依赖单一来源。

### 7.3 概念课③：互联网的本质就是目录服务

目录服务栈（同一套「定位资源」思维的三层落地）：

| 层 | 机制 | 说明 |
|---|---|---|
| **DNS** | 名字 → 地址 | 层级域名 + 委派（RFC 1034/1035），把 `example.com` 解析成 IP |
| **URL** | 路径定位 | 绝对 URL = 基址 + 相对路径（RFC 3986），与安装包相对路径同构 |
| **apt 仓库** | 包目录 | suite/component/arch + `Packages` 索引，本质是「包的名字→文件」目录 |
| **搜索引擎** | 倒排索引 | 把内容映射成可检索条目，是目录服务的派生形态 |
| **根 DNS** | 目录的目录 | 13 组根服务器把顶级域委派给注册局，是目录服务栈的 apex（后期演化终点） |

- **安全衍生**：目录投毒（DNS 劫持 / 伪造索引）对信任锚（DNSSEC / GPG 公钥）；
- **隐私衍生**：查询日志泄露兴趣，故有 DoH / DoT；
- **需求扩展**：算力 / 实时 / 身份，仍是「在命名空间里定位资源」的延伸。

### 7.4 概念 refinement（用户后续补正）

- **冗余允许但非不用；有些冗余为适老化与无障碍**：目录 / 服务的「重复」有时是必要设计——多入口（同服务的镜像 / 多 URL）、别名路径（`/bin` 与 `/usr/bin` 并存）、可读化命名（汉字目录名便于银发用户与 a11y 访问）。原则是「允许冗余但不是不用」：明确的别名与镜像是可达性的保障，但每个副本都要可追溯、可清点（本工具的检测面正是对这种冗余做资产登记）。这与「过度 DRY」形成对照——在可达性面前，适度的重复是值得保留的成本。
- **目录即服务的后期演化 = 根服务器 DNS**：目录服务栈从本地目录 → 包仓库 → URL → 普通 DNS 一路向上，其顶点是 13 组根服务器——它们是「目录的目录」，把顶级域委派给各注册局。根服务器 DNS 是目录服务演化的 apex，也是整张互联网目录之网的信任根；理解这一点，就把「相对路径 → 仓库寻址 → DNS 解析 → 根委派」串成了同一条目录思维链。

## 9. 诚实边界（needs_verify 清单）

1. **各发行版 usrmerge 完成度**：不同版本 `/bin` 是否已符号链接到 `/usr/bin`，以本机探测为准，不代发行版下结论。
2. **GPG 公钥分发的「信任锚软肋」具体利用案例**：公钥经 `curl` 拿 `.gpg.key` 落地，存在中间人风险，但具体历史案例未逐条核实。
3. **搜索引擎倒排索引实现细节**：仅作概念类比，未深入具体引擎实现。
4. **Metasploit 版本新鲜度口径**：msfconsole 自检副本超两周提示 `msfupdate`，新鲜度建议由 EOL 巡检统一管理。

## 10. 兼容层固化（native/common.py）—— 单一事实源 + 防误判冗余

「兼容并包」的共享能力落在 `native/common.py`：它是 sysweeper **唯一的**跨子系统共享工具库，
被 40+ 个 native 子系统 `from . import common` 引用（命令执行 / 字节格式化 / 磁盘用量 /
缓存·临时·大目录只读盘点 / DNS 缓存指引 / 多系统无障碍探测）。本次把它**固化为显式库**：

- **公开契约**：补 `__all__`（15 个公开符号），任何消费方 `from common import *` 只拿到契约内 API。
- **机器可读身份**：`__role__ = "shared_compat_lib"` + `__canonical__ = True` + `__version__`
  标记它是兼容层正典，而非通用/冗余工具文件。
- **强自述**：模块 docstring 显式声明「本模块就是兼容层，不是任何文件的副本或冗余」，
  并指出扩展方式（本文件内增函数并更新 `__all__`，或新建语义不同的模块）。

**防误判冗余**（直接针对历史上振荡/还原事故产生的幽灵副本，如 `sysweeper` 拼写错误的
三 e 副本 `sysweerer`）落到 `tests/test_native_common_lib.py`，三道防线：

1. **身份契约**：`__role__`/`__canonical__`/`__version__` 齐全，`__all__` 符号全部真实存在且可调用。
2. **实际被依赖**：统计 `common.py` 被引用次数（阈值 ≥30），证明是被依赖的共享库而非无人使用的冗余文件。
3. **冗余侦测**：全 native 包 `__role__` 不得重复（重复即幽灵副本）；且不得出现 `common` 的
   编辑距离 ≤1 形似副本（commonn / commons / commom …），包层不得出现 `sysweeper` 的拼写错误副本。
   验证：注入 `commonn.py` 时两条侦测测试即时 FAIL，删除即恢复全绿。

> 设计取舍：`sysbase` 私有 `_run` 与 `common.run` 虽功能相近，但前者用 `LC_ALL=C` + 布尔契约以稳定
> 解析 `dpkg`/`rpm` 输出，属领域变体（各自系统的事），**不强行合并**以免改掉检测行为；真正共同的
> 骨架已通过 `common.py` 兼容并包。这正是对应用户「兼容并包」与「统合到各自系统」的张力。
