# 版本号体系：去中心化格式与各自独立版本

> 引入时间：2026-10-23（基于 v0.6.88 重构批准）；2026-10-24 monorepo 统一扩展
> 配套模块：[`src/python/sysweeper/version.py`](../../src/python/sysweeper/version.py)
> 配套测试：[`tests/test_version.py`](../../tests/test_version.py)

## 一、为什么要改

旧版采用单一全局版本 `0.6.xx`（三段式语义化），所有层——整体包、兼容层、概念
系统、子系统——都被迫同步到同一个数字。这带来三个问题：

1. **一处改动要同步多处的脆弱**：改任何一层都要回头改全局版本，容易漏改、改错。
2. **推送提交过大**：为了迁就统一版本，有时会把无关改动一并塞进“版本同步”提交。
3. **语义不清**：全局版本到底代表谁的成熟度，长期含糊。

本重构把版本号**去中心化**：每一层**各自持有独立版本号**，互不同步；改一处只 bump
自己。整体包五处活版本（Python `version.py` / `pyproject.toml` / Go `main.go` / Deno
`console.ts` / `report_viewer.ts`，含头注释与 DEMO schema 串）仍保持等值——因为那是
同一个发布产物，必须一致——但**不复用**作其他层的版本。

## 二、新格式

```
NNNN.NNNN.NNNN.NNNN[.YYYYMMDD]
```

- 核心计数为 **4 段**，每段 **4 位零填充**（`0000`–`9999`）。
- 末尾**可选** 8 位日期后缀 `YYYYMMDD`（≤ `99991231`），记录该版本的定版 / 发行日期。
- 省略日期后缀即**基值形态** `0000.0000.0000.0000`（“没有后面”）。

示例：

| 含义 | 版本串 |
| --- | --- |
| 首发（整体包） | `0000.0000.0000.0001.20261023` |
| 兼容层独立契约 | `0000.0000.0000.0088.20261023`（保留原 0.6.88 的成熟度 88） |
| 基值（无后缀） | `0000.0000.0000.0000` |
| 上限 | `9999.9999.9999.9999.99991231` |

> 注意：新格式**不是** PEP 440 版本号。但我们**不**用 setuptools 打包，而是用仓库自带
> `tools/syspkg.py`（手写 PEP 427 wheel / sdist，纯标准库、对版本格式零依赖），因此
> 偏离 PEP 440 不会触发任何构建失败，五处活版本可稳定保持 odometer 格式。需要 PEP 440
> 串（如 PyPI 发布）时，用 `version.to_pep440()` 单独映射，不改动五处活版本。
> 见文末“打包路径（已定）”。

### semver 强制场景：CalVer `YYYY.MM.DD`

凡工具链强制 3 段 semver 的位置（Cargo.toml / package.json），改用 **CalVer**
`YYYY.MM.DD`（如 `2026.10.24`）——与 odometer 的日期后缀同源、**年份打头显长青**，
由 `version.to_semver()` 统一映射（`0000.0000.0000.0001.20261023` → `2026.10.23`）。
Cargo 场景下 `Cargo.lock` 的对应条目同步手改，`cargo metadata --offline` 实测一致。

## 三、里程表式进位（odometer）

4 段是**里程表式**的：最右段 **D** 为主序号，溢出时向左进位（D → C → B → A）。

- `0000.0000.0000.9999` → `0000.0000.0001.0000`（D 溢出进 C）
- `0000.0000.9999.9999` → `0000.0001.0000.0000`
- `9999.9999.9999.9999` → **`0000.0000.0000.0000`**（四段全满 → 循环归零）

`version.bump(v, *, date=None)` 实现该语义：

- `date=None`（默认）：进位后**追加当日日期** `YYYYMMDD`；
- `date=""`（空串）：只推进核心计数，**去掉日期后缀**；
- `date="20260101"`：用显式日期。

## 五、工具 API（`sysweeper.version`）

纯标准库、零依赖、无循环导入（不 import 包内其他模块）。

- `CORE_RE` / `FULL_RE`：核心 4 段 / 完整形态（核心+可选 8 位日期）正则。
- `PACKAGE_VERSION` / `BASE_VERSION`：整体包事实源与基值常量。
- `is_valid(v)`：是否合法（结构匹配 + 日期月/日合理 + ≤ `99991231`）。
- `today_suffix()`：当日 `YYYYMMDD`。
- `bump(v, *, date=None)`：里程表进位 + 循环归零 + 默认追加当日日期。
- `strip_date(v)`：取下日期后缀的基值。
- `to_pep440(v)`：将 odometer 版本映射为 PEP 440 串（仅外部 PEP 440 工具需要，不改五处活版本）。
- `to_semver(v)`：将 odometer 版本映射为 CalVer `YYYY.MM.DD`（供 Cargo/npm 等 semver 强制场景，年份打头）。

模块导入即运行 `_self_check()`，验证核心不变量（进位 / 循环 / 格式 / 映射）。

## 六、打包路径（已定：走 syspkg，对版本格式零依赖）

`pyproject.toml` 持非 PEP 440 版本串 `0000.0000.0000.0001.20261023`。早期方案是用
`setuptools`（`python -m build`）打包，会按 PEP 440 校验 `project.version` 而**可能失败**，
且不同模型接手时可能为“合规”把三处活版本改回 PEP 440、破坏一致约束。

**已定决策**：改由仓库自带 `tools/syspkg.py` 打包（手写 PEP 427 wheel / sdist，纯标准库、
不经由 setuptools），对版本格式**零依赖**——版本串原样写入 wheel 名与 METADATA，不触发
任何 PEP 440 校验。落实点：

- `.github/workflows/build.yml`：打 `v*` tag 时用 `python3 tools/syspkg.py wheel sdist`
  产出并附到 Release（不再调用 `python -m build`）；
- `system-optimizer/Dockerfile`：构建阶段同样调 `tools/syspkg.py`，运行阶段 `--no-index`
  只装本构建产出的 wheel；`docker-compose.yml` 的构建上下文设为仓库根（`context: ..`）；
- 实测：`syspkg` 产出的 wheel 在全新 venv 中以 `--no-index` 安装成功，`__version__`
  正确回填，证明该路径对 odometer 版本完全免疫。

仅当必须对接强制 PEP 440 的外部系统（如 PyPI）时，才用 `version.to_pep440(v)` 单独映射
（如 `0000.0000.0000.0001.20261023` → `0.0.0.1+20261023`），**不改**三处活版本。
