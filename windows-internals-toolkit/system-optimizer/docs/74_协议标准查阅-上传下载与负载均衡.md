## 二、边界分级与诚实边界

- **传输层与可靠性（部分可对照）**：TCP/QUIC 的「可靠有序、重传、拥塞控制、ECN」原则，与本仓 `meshchat` 的**安全底线**（收到的东西不自动落盘、超大载荷超限拒绝、对方显式请求才建 TCP 取）在「不信任对端、可拒绝、可上限」精神上同构；但本仓**无字节级传输引擎**（真实文件字节走 TCP 且推迟到上层 manual），更无 QUIC/拥塞控制实现。
- **文件上传/下载协议（几乎无 counterpart）**：FTP/FTPS/SFTP/WebDAV/NFS/BitTorrent 均为**外部协议实现**，本仓**不克隆不构建**；本仓仅 `meshchat.send_files` 做 IPMsg 属性通知 + 按需 TCP 拉取（属写操作交上层）。LinkSwift 多线程字节拉取（`docs/73`）亦属外部用户脚本，本仓无 counterpart。
- **负载均衡与可用性（无 counterpart）**：Anycast / 一致性哈希 / 熔断 / ECMP / L4-L7 LB 均属**服务端/基础设施**范畴，本仓 monorepo 无该层，仅 `meshnet` 静态节点表与 `distcompute` 硬指标上限调度可对照「用硬上限而非信任做调度」的思路。
- **安全基线（原则可复用，实现无）**：TLS 1.3 的「前向安全 + 1-RTT」、HTTP `429` 限流、`ETag`/`Digest` 完整性校验、SFTP/FTPS 凭证不落地——其**工程纪律**（传输加密 + 完整性校验 + 限速自约束 + 凭证不外发）可作为普适原则，留待本仓未来真做字节传输时采纳。

诚实边界重申：标准号以 IETF RFC Editor / HTTP WG / QUIC WG 发布为准（已逐一标注）。吞吐量对比（如 SFTP 10–50 MB/s、SMB 3.x 多通道饱和千兆等）来自第三方评测文章，**未独立复现**（`needs_verify`）；SFTP / BitTorrent / 一致性哈希 / 熔断**非 IETF RFC**（分别为 SSH 草案、BEP、MIT 论文、设计模式），按事实口径记录。

## 三、分主题学习笔记

### 3.1 传输层与可靠性：TCP → QUIC 的演进

- **TCP（RFC 9293）** 是 FTP/SFTP/HTTP/1-2 的底座：三次握手、按字节流可靠有序交付、重传、拥塞控制。拥塞控制算法族：Reno（RFC 5681）、NewReno（RFC 6582/6675）、**CUBIC（RFC 9438，2023，废 8312，Linux/Windows/Apple 默认）**、ECN（RFC 3168/8311）。CUBIC 乘性降窗因子 0.7（Reno 为 0.5），大 BDP 长肥管道下比 Reno 利用率高。
- **QUIC（RFC 9000/9001/9002）** 把传输可靠+TLS1.3+流多路复用**下沉到 UDP 之上**：流级可靠、整连接级拥塞控制（拥塞窗口以字节计、per-path）；0-RTT 建连、路径迁移（换网不断）、免 TCP 队头阻塞。HTTP/3（RFC 9114）即 QUIC 之上的 HTTP 语义映射。拥塞控制默认类似 NewReno，允许换 CUBIC（遵循 RFC 8085 指南）。
- **可复用纪律**：① 「**用硬上限而非信任做调度**」↔ 本仓 `distcompute`「预算硬上限、绝不下载执行外部代码」同构；② 「**失败可重传、拥塞可退避**」↔ 本仓应急/网络抓取失败重试与退避同构。

### 3.2 文件上传 / 下载协议：从明文到加密、从单连接到分块并行

- **FTP（RFC 959）→ FTPS（RFC 4217）**：命令/数据双通道（21/20），明文无安全；FTPS 加 TLS（显式 AUTH / 隐式 990）。FTP 扩展 RFC 3659 提供 `REST` 断点续传、`MLSD` 目录列举。
- **SFTP（SSH-2，RFC 4251/4253）**：单 SSH 连接（22）内加密做完整文件管理，**按字节偏移断点续传**；SCP 更简单但不支持续传与浏览。
- **WebDAV（RFC 4918）**：HTTP 扩展，写锁（LOCK/UNLOCK）防并发冲突、支持版本化与 HTTP Range 续传，适合协作式文件管理。
- **HTTP Range（RFC 9110 §14.3.3）+ 206 Partial Content + ETag/Digest（RFC 9530）**：这是**分块断点续传与完整性校验的事实底座**——客户端按 byte-range 并行取多段、用 `ETag`/`Digest` 校验每段，拼回完整文件。LinkSwift（`docs/73`）的多线程加速正是这一机制在网盘直链上的工程化。
- **BitTorrent（BEP 3）**：piece（分块）+ block（分片）两级、**piece hash 逐块校验**、多源并行、tit-for-tat 速率公平，断点续传天然。
- 可复用纪律：① 「**分块 + 偏移续传 + 逐块校验**」↔ 本仓未来字节传输引擎的必备三件套；② 「**凭证不落地、本地解析**」↔ `meshchat`「不自动落盘」+ `distcompute`「不收外部代码」同构。

### 3.3 负载均衡与可用性：DNS / Anycast / 哈希 / 熔断

- **DNS 轮询 + Anycast（RFC 1546/2526，BCP 126=RFC 4786）**：多服务器共享同一 IP，BGP 按路由度量就近；DNS 部署最广泛，提供就近接入、故障自动绕行、DDoS 负载摊薄。
- **一致性哈希（Karger 1997）**：节点增减只重映射邻近区间，满足单调性/均衡性/分散性/负载四条件，是「分布式容错 + 弹性扩缩」的寻址基石（L4 LB 用 ECMP（RFC 2991/2992）按五元组哈希分发到边缘）。
- **L4 / L7 负载均衡**：L4（传输层，按 IP/端口）与 L7（应用层，按 HTTP 头/路径）分流；健康检查剔除不可用后端；**熔断（Nygard）**以闭合/半开/断开三态防级联雪崩；**重试 + 指数退避**避免惊群。
- 可复用纪律：① 「**硬指标上限 + 健康检查 + 熔断**」↔ 本仓 `distcompute`「预算硬上限 + 校验比计算便宜」的可用性防御思路同构；② 「**就近 + 冗余自动绕行**」↔ `meshchat` 多节点广播、单点不可达不阻塞整体同构。

### 3.4 安全基线：传输加密 + 完整性 + 限速自约束

- **TLS 1.3（RFC 8446）** 前向安全、1-RTT；QUIC 内置、HTTPS 必备。
- **HTTP 限流**：`429 Too Many Requests`（RFC 6585）+ `Retry-After`；`103 Early Hints`（RFC 8297）提前推资源。
- **完整性**：`ETag`（RFC 9110）+ `Digest` 字段（RFC 9530）使「下载即校验」可标准化。
- 可复用纪律：上述三件套（加密 + 校验 + 限速）与 `docs/73` 记录的 LinkSwift「带宽/并发上限自约束、本地解析不收凭证」完全一致，可作为本仓**未来字节传输引擎**的统一安全基线。
