# xnu-hd2 分析与应用

> 参考对象：<https://github.com/Garysss123/xnu-hd2>
> 一句话概括：**给一台 2010 年的手机（HTC HD2 / HTC Leo，Qualcomm QSD8250，ARMv7 Thumb）
> 移植 XNU 内核与板级支持**。C，27 stars，源树上一次推送 2026-10-08。
> 上游基线：`HTC-Leo-Revival-Project/xnu` @ `d5c85d9`。

## 1. 它是什么

| 项 | 内容 |
|---|---|
| 目标硬件 | HTC HD2（Leo），QSD8250，ARMv7 Thumb —— **单核 1 GHz、576 MB RAM 级别** |
| 移植内容 | CPU/中断/定时器初始化、RAM 映射、SDCC 存储、MDP 显示扫描输出、Type2A 触摸，IOKit 显示/HID 服务 |
| 目录分工 | `xnu/` 内核树（HD2 部分在 `xnu/pexpert/arm/` 与 `xnu/iokit/Drivers/KernelBuiltIn/ARM/AppleARMPlatform/`）；`network-port/` 网络栈兼容头；`nokextd/` 编译期能力 flag（`meta_features.h`） |
| 明确不做 | 只含源码，**不含** Apple userland、根文件系统、缓存、固件、启动镜像、SDK、工具链二进制、运行日志、卡身份信息 |

## 2. 值得学的四条工程纪律（本轮直接应用）

真正有价值的不是它的 C 代码（与本项目无关、也不该引入），而是它**把移植这种高风险工程写成可复核的方式**。

### 2.1 静态审计要写明"不证明什么"

`SOURCE-AUDIT.md` 开篇即声明：

> It does not compile code, preprocess every target option, or establish boot or hardware acceptance.

并且把"扫到的 include 未解析"定性为 **candidate reference，not proof of an active missing dependency**。

**本项目应用**：本轮新增的安卓 8/14 构建脚本（`tools/build_android.py`）只生成目标配置并做**静态自检**，
在输出里明写「未在本环境编译/未上真机验证」——不把"配置生成成功"说成"构建成功"。
这与项目既有的「只读优先、缺依赖就说跳过」是同一条纪律。

### 2.2 区分「源码」与「生成产物」，别把生成物当缺失源码补

审计发现 common `files` 清单里有 43 行缺失，但**没有一股脑报成"缺文件"**，而是拆开：

- 39 行 `./...` 是构建产物（4 个 BSD 输出 + 35 个 OSF/MIG 输出），由 `makesyscalls.sh`、
  `osfmk/mach/Makefile`、`config/mkioconf.c` 生成 —— **不该手搓**；
- 4 行是 SL/TUN/PPP 可选驱动，而受检配置把它们设为 0，因此**在当前配置下不生效**。

**本项目应用**：能力清单要区分**三态**，不能只有"有/没有"：

| 状态 | 含义 | 例子 |
|---|---|---|
| `present` | 探测到且可用 | 4 核 CPU 空闲率 70% |
| `generated` | 由别的东西派生，缺的是上游不是它本身 | 编译产物、缓存索引 |
| `inactive` | 存在但被配置/策略关掉 | 用户停用的插件、TUN=0 的驱动 |

本轮 `distcompute` 的节点能力报告就按这三态输出，避免把"策略关闭"误报成"硬件缺失"。

### 2.3 清单 + SHA-256 + 自检脚本，让"复现"可复核

`SOURCE-MANIFEST.sha256` + `tools/check_source_completeness.py`：校验哈希、检查架构相关
`files.arm` 里的路径、跟踪本地可解析的 include 闭包（且**先剥掉 C/C++ 注释再扫**）。

**本项目应用**：`tools/build_android.py` 产出的目标配置带**内容指纹**，
重跑同一目标指纹不变即可判定"配置没漂移"；指纹变了才需要人工复核。

### 2.4 环境缺失时，说清替代手段与"哪一步没跑"

审计里 Python 3 不可用，作者用 Node.js 移植重算了计数，**同时写明 Python 版脚本未在此执行**——
既不假装跑过，也不因跑不了就放弃结论。

**本项目应用**：与既有纪律一致（缺库写"跳过"、OpenCC 仅生成期依赖）。
本轮安卓构建脚本在没有 NDK/adb 时，输出"未构建（缺 X）"而不是假装成功。

### 2.5 老设备不是电子垃圾，是可以重新上岗的算力（本轮的真正启发）

HD2 这种 2010 年的单核 ARMv7 机器，靠板级移植能跑起全新内核。
这直接支撑本轮的用户诉求：**安卓 8 那批老设备不该被淘汰，入网后可以捐献算力**。

设计上的三点适配（落在 `native/distcompute.py` 与安卓任务里）：

1. **弱机也能捐**：工作单元（WU）按设备能力切分——老机拿小粒度、低内存占用的任务，
   不因为"跑不动大任务"就把设备排除。
2. **弱机先保自己**：调度前看负载/电量/是否计量网络；老设备上限制并发为 1，
   且电量低或温度高时不派活——**捐算力不能把本机拖垮**。
3. **结果必须可复算校验**：老设备可靠性更低，所以 WU 冗余双投、结果不一致不记账
   （详见 distcompute 模块说明）。

## 3. 明确不引入的东西

- ❌ 不引入其任何 C 源码、头文件、构建产物 —— 目标平台（ARMv7 + XNU）与本项目（Python
  标准库、跨 8 个平台）无交集，且许可证为 `NOASSERTION`（未明确授权），**按边界处理，不碰**。
- ❌ 不声称"能在 HD2 上跑" —— 本项目在安卓上的能力走 adb/只读探测，与该移植无关。
- ✅ 只借鉴**工程方法**：审计边界声明、三态能力清单、清单+指纹自检、诚实降级。

## 4. 与本项目既有纪律的对照

| xnu-hd2 的做法 | 本项目对应 |
|---|---|
| 静态审计声明"不证明能启动" | 只读任务声明"只分析不改系统"；构建脚本声明"未上真机验证" |
| 39 条生成产物不当缺失源码 | 缺库写"跳过"；策略关闭 ≠ 硬件缺失（三态） |
| SHA-256 manifest 保可复核 | 快照对比（`native/snapshot.py`）、配置指纹 |
| 环境缺失说清哪步没跑 | 优雅降级、OpenCC 仅生成期、离线时"查不到就说明查不到" |
