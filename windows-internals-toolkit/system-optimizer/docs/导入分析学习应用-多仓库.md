# 导入分析学习应用：多仓库整体分析（v0.6.14）

> 缘起：用户要求把若干高质量开源项目「整体导入、分析、学习、应用」到本工具。
> 边界（全项目红线）：**只读、不执行、不写系统、不引入需要联网调用 LLM 的运行时**。
> 因此「应用」分两类：① 直接落地为**代码模块**（最贴切的 Proton）；② 吸收其**架构原则**沉淀为设计理念（litebox 的隔离、5 个 AI 项目的「隔离/审计/可接管」），不突破红线。

---

## 1. ValveSoftware/Proton —— ✅ 已落地为 `native/proton.py`

**本质**：Steam Play 兼容层，让 Windows 独占游戏跑在 Linux 上。基于 **Wine** 深度定制（Valve + CodeWeavers 自 2016 年联合开发）。用户量最大的跨平台兼容层。

**技术栈（已吸收为诊断坐标系）**：

| 组件 | 职责 | 本工具如何复用 |
|---|---|---|
| **Wine** | 把 Windows NT API（kernel32/ntdll/user32/d3d*/dxgi…）翻译成 POSIX/类 UNIX | 作为兼容层的总前提背景 |
| **DXVK** | D3D9/10/11 → Vulkan（替代 Wine 内置软 D3D，大幅降 CPU 开销） | 诊断 Vulkan 支撑栈是否就绪 |
| **VKD3D-Proton** | D3D12 → Vulkan（Wine 原生不支持 DX12） | 同上（DX12 依赖 Vulkan） |
| **wine-mono** | .NET Framework 运行时替代 | 安装现状核验 |
| **Steam Runtime (steamrt)** | 基于 Debian/Ubuntu 的运行时容器，scout/soldier/sniper 三代，pressure-vessel 容器化保 ABI | Steam Runtime 安装/进程核验 |

**Runtime Config Options（官方 README 全表，已作为诊断判定依据）**：

| 选项 | 变量 | 含义 |
|---|---|---|
| `wined3d` | `PROTON_USE_WINED3D` | 用 OpenGL wined3d 替代 Vulkan DXVK（d3d9/10/11），性能差但兼容老驱动 |
| `nod3d11` | `PROTON_NO_D3D11` | 禁用 d3d11.dll，让游戏回退 d3d9 |
| `nofsync` | `PROTON_NO_FSYNC` | 禁用 futex 同步（系统无 `FUTEX_WAIT_MULTIPLE` 时自动禁用） |
| — | `PROTON_NO_NTSYNC` | 禁用 ntsync |
| `disablenvapi` | `PROTON_DISABLE_NVAPI` | 禁用 NVIDIA NVAPI |
| `hidenvgpu` | `PROTON_HIDE_NVIDIA_GPU` | 把 NVIDIA 强制报成 AMD（部分游戏依赖 Windows 专属 N 卡功能） |
| `gamedrive` | `PROTON_SET_GAME_DRIVE` | 创建 S: 盘指向游戏所在 Steam 库 |
| `PROTON_LOG` | — | 导出调试日志到 `$PROTON_LOG_DIR/steam-$APPID.log` |
| 已废弃 | `seccomp`(5.13) / `d9vk`(5.0) / `noesync`(11.0) | 历史选项，已知会 |

**已落地**：`native/proton.py` 全只读诊断 —— Vulkan 支撑栈(loader+ICD) / 32 位 i386 运行时 / NT 同步原语(esync·fsync·NTSync) / Steam Runtime 与 Proton-Wine 安装，逐项给结论与修复提示。注册到 `registry` / `cli`(`proton`) / `gui`(兼容层诊断) / `tasks`(`proton_report`)。

## 2. microsoft/litebox —— ✅ 已吸收为「兼容层隔离」原则

**本质**：微软安全沙箱**库操作系统**（Rust，MIT）。暴露类 `nix`/`rustix` 的 **North** 接口，下接 **South** 平台接口，大幅削减对宿主的接口面以降低攻击面。支持 kernel 与 non-kernel 场景。

**用例**：在 Windows 上跑未修改的 Linux 程序 / 在 Linux 上沙箱化应用 / 跑在 SEV-SNP 机密计算 / 跑 OP-TEE / 跑在 LVBS。

**与本工具关系**：其「**接口面削减 / 隔离 / 最小权限**」理念直接支撑本工具的兼容层运行原则——写入 `proton.proton_report` 的运行原则段与 `native/__init__` 的 `proton` 模块说明：兼容层应在最小权限、可审计、可接管环境中运行。

## 3–7. 五个 AI Agent / 个人助理项目（诊断隔离理念的参考源）

| 仓库 | 本质 | 技术栈 / 许可 | 关键能力 |
|---|---|---|---|
| **elie222/rakazo** | 开源 Grok Bot 替代（自托管 AI 聊天） | AI 聊天 bot | 自托管、类 Grok 交互 |
| **milind-soni/OpenMausBot** | 本地优先多智能体聊天桌面应用 | TypeScript，Apache-2.0 | 给 bot 配**虚拟机**让其使用；本地优先 |
| **CopilotKit/openmuse** | 个人 AI 助理（给 Agent 配「电脑」） | CopilotKit + Intelligence | 持久化浏览器 / **可选 Linux 容器** / 文件系统；任务后台持续运行、可暂停接管；集成 Gmail/Calendar/PDF/记忆 |
| **CopilotKit/OpenDots** | 自托管 7×24 常驻 AI 同事 | CopilotKit + AG-UI | 操作浏览器 / 终端 / 读写本地文件系统；多 Dot 工作台（每 Dot 独立角色与工具权限） |
| **Anil-matcha/open-dots** | OpenAI Dots 开源平替 | Python + Next.js，MIT | 本地模型 Ollama 桥接；聊天 / 审批 / 审计 |

**共同架构模式（已提炼为可借鉴原则）**：
1. **本地优先**——数据留在自有基础设施，不强制上云。
2. **隔离执行**——给 Agent 配沙箱 / 容器 / 文件系统 / 终端，而非裸奔在宿主。
3. **可审计**——操作留痕、可审批（open-dots 的「审批/审计」是其核心机制）。
4. **可接管**——人随时能暂停、接管 Agent 正在做的事（openmuse 的「随时接管」）。
5. **常驻 + 编排**——多 Agent 协作（OpenDots 的 Dot 工作台、AG-UI 协议串联）。

**与本工具关系**：
- ✅ **已吸收**：把「隔离执行 + 审计 + 可接管」升级为本工具的诊断隔离理念——本工具所有 native 层本就只读、动作 opt-in、报告可审计，与上述原则同源。未来若引入 AI 辅助运维，应遵循此模式（隔离环境运行、操作留痕、人可接管）。
- ⛔ **不适用**：直接把这些项目的 LLM 运行时（需联网调用模型 API）塞进本工具——会突破「只读、不写系统、不连校外网做写」红线。故仅作设计参考，不引入运行时。

## 8. 融合结论

| 仓库 | 处置 | 落点 |
|---|---|---|
| Proton | **代码落地** | `native/proton.py` + cli/gui/tasks/registry |
| litebox | **原则吸收** | 兼容层「隔离/最小权限」运行原则 |
| rakazo / OpenMausBot / openmuse / OpenDots / open-dots | **原则吸收** | 诊断隔离理念（隔离/审计/可接管/本地优先） |
| （全部） | 红线约束 | 不引入 LLM 运行时、不写系统 |
