# v0.6.36 · 闭环：缺口分类与按需补齐

> 承接 v0.6.35「全能全知自检」——那一轮让工具能精确说出自己哪儿不知道。
> 这一轮解决一个问题：**全知不能停在「我知道我缺什么」，得能说出「怎么补」**。

## 1. 动机：从「全知」到「闭环」

v0.6.35 的 `omni` 三层自检跑完，暴露了一个刺眼的数字：

- 登记 64 项能力，CLI / GUI 入口 **63/64**——有 1 项真缺口（`fonts` 只差 GUI 面板）；
- 四件套齐全只有 35%——剩下 65% 被标成「半截能力」。

但细看那 65%，**大半不是真欠账，是「设计如此」**：

- `subsystems` / `linkage` / `omni` 是工具自身的骨架（清单 / 联动 / 自检），它们本就不是诊断探针，没有独立的「任务」或「知识库」；
- `settings` / `importio` / `snapshot` / `distjob` 是机制类（参数注册表 / 导入机制 / 基线采集 / 调度），同理。

把「设计如此」和「真欠账」混在一起，会让「四件套齐全 35%」这个数字误导读者，也让人误以为要补 40 多项。**真正该补的，是诊断类能力里那些缺入口的项**——而且每一项的补法都该具体到「改哪个文件、加哪个函数」。

这轮就做三件事：

1. 把缺口**分类**（设计如此 / 真缺口），让比例变诚实；
2. 给真缺口**可执行补法**（补哪个文件、加哪个入口）；
3. 提供**按需脚手架**（`gen-stub`）一键长出知识库占位，并**真正补掉那个唯一的 GUI 缺口**。

## 2. 缺口分类：设计如此 ≠ 半截能力

`native/omni.py` 新增 `BY_DESIGN_KEYS`（7 项）与 `_is_by_design()`：

| key | 为什么设计如此 |
|---|---|
| `subsystems` | 它是统一清单本身，没有独立的任务/知识库 |
| `linkage` | 它是联动轴体检，不是诊断探针 |
| `omni` | 它是自检层本身 |
| `settings` | 参数与阈值注册表即其数据来源 |
| `importio` | 多来源导入是机制，不是诊断维度 |
| `snapshot` | 快照/对比是基线采集机制 |
| `distjob` | 跨机派活是调度机制 |

`remediation_plan()` 对每一项缺口产出：

- `by_design=True` → 动作写「设计如此：<理由>」；
- `by_design=False` → 动作写具体补法（按缺的落点展开）：

  | 缺的落点 | 补法 |
  |---|---|
  | `cli` | `cli.py` 加 `def cmd_<key>(args)` 并注册 sub parser |
  | `gui` | `gui.py` 加 `def show_<key>(args)` 面板并在底部按钮行登记 |
  | `task` | `tasks/<key>.py` 加任务定义并注册到 TASKS |
  | `data` | `data/<key>.json` 加知识库（可 `omni gen-stub <key>` 生成占位） |

CLI `omni gaps` 与 `omni_report` 的「补齐清单」段都走这套分类：真缺口先列、设计如此项单列说明。

## 3. 补掉那 1 个真 GUI 缺口

omni 自检唯一暴露的真 GUI 缺口是 `fonts`（字体与文本规范化）：CLI `cmd_fonts`、任务 `tasks/fonts.py`、知识库 `data/fonts_standards.json` 都在，唯独 GUI 没 `show_fonts` 面板。

本轮补 `gui.show_fonts`：

- 只读渲染 `nf.report_fonts()`（本机字体清单 / 重复项）+ `nf.text_normalize_report()`（文本规范化状态，UAX #15）；
- 不改动任何字体与文件；
- 在底部按钮行登记「字体与文本规范化」。

补完后 **CLI / GUI 入口 64/64 接全**（TASK 49/64、DATA 25/64 属设计如此或诊断类待补，不再计入「半截能力」误报）。

## 4. 按需脚手架：`omni gen-stub KEY`

为真缺口的 `data` 项生成**知识库占位 JSON**（纯数据，不碰代码）。

```bash
python -m sysweeper omni gen-stub osi          # dry-run：只回显将写入的内容，不落盘
python -m sysweeper omni gen-stub osi --write  # 真正创建 data/osi.json（占位，待你填权威来源）
```

占位结构（生成的只是带 `_note` 的空壳，不自动填充任何正文）：

```json
{
  "_note": "知识库占位（v0.6.36 gen-stub 生成）：OSI 七层。待你补全权威参考来源与条目。本工具只读引用，不自动填充正文。",
  "key": "osi",
  "label": "OSI 七层",
  "domain": "网络",
  "references": [],
  "items": []
}
```

**安全红线（四条）**：

1. **不覆盖**：`data/<key>.json` 已存在则跳过（返回「已存在，跳过（不覆盖）」）；
2. **默认 dry-run**：不传 `--write` 只回显，绝不落盘；
3. **安全拒做**：未知 key / 已齐全项 / 设计如此项都返回 `ok=False`，不生成；
4. **不自动填充**：生成的只是空壳，references/items 留给你填权威来源——绝不引用未核实出处、绝不写任何正文内容。

> 实现注：`gen-stub` 在动笔前会重新跑 `wiring()` 实时核对缺data状态；写盘后第二次调用会因 `wiring()` 已感知到该 data 文件而走「未缺 data」安全拒做路径——等价于幂等不覆盖。

## 5. 红线回顾

- 全程**纯计算、只读**：分类盘点只读本仓库源码文本；`gen-stub` 只写本地数据 JSON 占位，调任何诊断函数、不改任何系统状态、不采集任何信息。
- 与 v0.6.35 一致：本工具不删系统文件、不改配置、不启停服务、不刷固件、不采集生物特征/定位/音视频/文件正文/通信内容、不保存任何账号凭证。

## 6. 测试
